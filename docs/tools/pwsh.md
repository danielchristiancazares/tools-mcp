## 3. Scope

### 3.1 What This Document Covers

`Pwsh` is the MCP tool that spawns the host's PowerShell 7+ binary (`pwsh` / `pwsh.exe`) with `-NoLogo -Command <command>`, captures bounded stdout and stderr, strips ANSI escape codes, and returns the exit code and outputs to the caller. The tool is owned by the `tools-mcp-local` crate; the entry point is `execute_pwsh` in `tools-mcp-local/src/tools/pwsh.rs:51`, and the type/schema is declared via `define_mcp_tool!` at `tools-mcp-local/src/tools/pwsh.rs:145-171`. Registration is gated behind the `MCP_ENABLE_PWSH_TOOL=true` environment variable; when the gate is unset, the tool is NOT placed in the registry at all (`tools-mcp-local/src/tools/mod.rs:30-36`).

### 3.2 Explicitly Out of Scope

- JSON-RPC framing and method routing (covered in `docs/protocol.md`).
- The composition-root registration call (`tools_mcp_local::register_tools` invoked from `tools-mcp-server/src/composition.rs:88`).
- Other process-execution tools that share `wait_with_limits` (the git tools); each has its own SDD.
- The threat model and adversary assumptions (covered in `docs/tools-mcp-threat-model.md`).
- Sandboxing or command allowlisting — the tool intentionally executes arbitrary shell commands and relies on the deployment-time gate as its only control surface (see §7).

When the gate is unset, calls to `mcp/tools/call { name: "Pwsh" }` reach the registry, find no executor, and the server returns a JSON-RPC method-not-found / tool-not-found response generated by the central dispatcher rather than any error surfaced by this tool's code path. The handler itself is never invoked. The README's tool-inventory contract test enables the gate explicitly so that the documented tool list and the live `mcp/tools/list` match (`tools-mcp-server/tests/golden_contract.rs:240-250`).

### 4.2 Invariants

The following invariants MUST hold on every invocation that reaches the handler (i.e., the registration gate is set):

- **Registration gate is read at startup, not per-call** — `MCP_ENABLE_PWSH_TOOL` is consulted exactly once during `register_tools` (`tools-mcp-local/src/tools/mod.rs:30`). Changing the variable after the server is running has no effect; the tool's presence is fixed for the server's lifetime.
- **Working directory MUST resolve inside the server working directory** — `working_dir` is passed through `path_policy::resolve_existing_directory` (`tools-mcp-local/src/tools/pwsh.rs:63`) which canonicalizes the path and rejects anything outside the canonical server cwd (`tools-mcp-local/src/path_policy.rs:47-63`). When `working_dir` is omitted, the tool resolves the literal `"."` against the same workspace policy (`tools-mcp-local/src/tools/pwsh.rs:57,63`).
- **Working directory MUST exist and be a directory** — `resolve_existing_directory` returns an error if the resolved path does not exist or is not a directory (`tools-mcp-local/src/path_policy.rs:53-62`).
- **Timeout MUST be clamped to `[100, 300_000]` ms** — `validation::clamp_timeout` enforces the range, applying the 60_000 ms default when the caller omits the value (`tools-mcp-local/src/tools/pwsh.rs:67-72`, constants at `tools-mcp-core/src/config.rs:25-28`).
- **stdout MUST be capped at 1_000_000 bytes; stderr at 500_000 bytes** — `wait_with_limits` enforces both caps before UTF-8 lossy conversion (`tools-mcp-local/src/tools/pwsh.rs:86-91`, constants at `tools-mcp-core/src/config.rs:31,34`). Truncation flags are echoed back in the response.
- **Timed-out children MUST be killed and waited within a 2 s grace period** — `wait_with_limits` kills the child on timeout and waits up to `KILL_GRACE_MS = 2_000` ms before propagating an error if the process refuses to exit (`tools-mcp-core/src/process.rs:21,153-169`).
- **ANSI escape sequences MUST be stripped from captured stdout and stderr** — `strip_ansi_codes` is applied after capture (`tools-mcp-local/src/tools/pwsh.rs:101-102`).
- **No panic on failure** — Every fallible step (argument parse, working-dir resolution, spawn, wait/capture) MUST translate into `ToolCallOutcome::err` (`tools-mcp-local/src/tools/pwsh.rs:54,65,80,97`). The handler MUST NOT panic.
- **`success` MUST be `true` iff exit code is 0 AND the process did not time out** — Computed in `ProcessResult` construction (`tools-mcp-core/src/process.rs:135`). The handler propagates this directly.
- **`isError` in the response MUST be the inverse of `success`** — `ToolCallOutcome::ok_json_content(&payload, !result.success)` (`tools-mcp-local/src/tools/pwsh.rs:120`). A non-zero exit code, a timeout, or any other non-success outcome produces `isError: true` even though stdout/stderr/exit_code are still returned as JSON.
- **Unknown argument fields MUST be rejected** — `PwshRequest` uses `#[serde(deny_unknown_fields)]` (`tools-mcp-local/src/tools/pwsh.rs:21`).

### 4.3 Explicitly Forbidden Shapes

- MUST NOT register the tool when `MCP_ENABLE_PWSH_TOOL` is unset or has any value other than the literal string `"true"` (`tools-mcp-local/src/tools/mod.rs:30`).
- MUST NOT execute the command if `working_dir` resolves outside the server's canonical working directory.
- MUST NOT spawn the child without `Stdio::piped()` for both stdout and stderr — `build_pwsh_command` configures the pipes (`tools-mcp-local/src/tools/pwsh.rs:42`), and `wait_with_limits` errors out before draining if pipes are missing (`tools-mcp-core/src/process.rs:100-113`).
- MUST NOT invoke `cmd.exe`, `powershell.exe` (Windows PowerShell 5.1), or any other shell. The only program names selected are `pwsh.exe` on Windows and `pwsh` elsewhere (`tools-mcp-local/src/tools/pwsh.rs:30-36`).
- MUST NOT block indefinitely on a hung child — the `tokio::time::timeout` wrapper around `child.wait()` MUST be in force (`tools-mcp-core/src/process.rs:121`).
- MUST NOT allow stdout or stderr to grow without bound, even if the child writes faster than the caller can consume — `read_to_end_limited` continues draining the pipe after the cap to prevent the child from blocking, but discards the overflow (`tools-mcp-core/src/process.rs:49-76`).
- MUST NOT return raw ANSI escape sequences in the response payload.
- MUST NOT panic; all failure paths MUST yield a `ToolCallOutcome`.

## 5. Design Goals

- **Disabled by default; opt-in by deployment.** Arbitrary host command execution is the highest-impact local capability in the registry (per the threat model, `docs/tools-mcp-threat-model.md`). The startup-time registration gate ensures that an operator who has not consciously enabled the tool cannot have it activated by a runtime argument, a request header, or a stale config file.
- **Cross-platform but PowerShell-only.** Picking `pwsh` (PowerShell 7+) on both Windows and Unix targets gives callers a uniform syntax. The tool deliberately does not fall back to the legacy `powershell.exe` or to a POSIX shell, so callers can rely on the command running through the same parser everywhere.
- **Bounded resource use.** Every dimension that an unbounded child could exploit (wall time, stdout bytes, stderr bytes) has a hard cap enforced by shared infrastructure (`wait_with_limits`). The cap is the same regardless of caller inputs; callers can lower the timeout but not raise it above 300_000 ms.
- **Confine commands to the workspace.** The `working_dir` is canonicalized through the project's path policy so that even a deliberate `..` traversal cannot move the spawn outside the server cwd. The command string itself is not sandboxed, however; see §7.

## 6. Tool Specification

### 6.1 Input Schema

| Field | Type | Required | Default | Constraints | Description |
|---|---|---|---|---|---|
| `command` | string | Yes | — | Non-empty in practice (deserialization accepts empty, but PowerShell will exit with the empty-command behavior) | The PowerShell command or expression to execute. Passed verbatim to `pwsh -Command`. |
| `working_dir` | string | No | `"."` | Resolved path MUST stay inside the server working directory; MUST exist; MUST be a directory. When provided, MUST contain at least one non-whitespace character. | Working directory for the spawned process. |
| `timeout_ms` | integer | No | `60000` | Clamped to `[100, 300_000]` after parse; schema declares `minimum: 100, maximum: 300_000` | Wall-clock timeout in milliseconds for the spawned process. |

The schema sets `"additionalProperties": false` (`tools-mcp-local/src/tools/pwsh.rs:168`); the deserializer also sets `#[serde(deny_unknown_fields)]` (`tools-mcp-local/src/tools/pwsh.rs:21`). Unknown fields produce a tool-level error (`isError: true`) with text `"invalid arguments: ..."` via `ToolCallOutcome::parse_args` (`tools-mcp-core/src/tool_outcome.rs:61-75`).

> Schema source: `tools-mcp-local/src/tools/pwsh.rs:149-169`. Request type source: `tools-mcp-local/src/tools/pwsh.rs:20-28`.

### 6.2 Behavior

Ordered execution steps. Each step is anchored to a code location.

1. **Parse arguments** — Deserialize `args` into `PwshRequest` via `ToolCallOutcome::parse_args` (`tools-mcp-local/src/tools/pwsh.rs:52-55`). On failure, return a tool-level error with `"invalid arguments: ..."` text (`tools-mcp-core/src/tool_outcome.rs:61-75`); the handler does not proceed.
2. **Select default `working_dir`** — If the caller omitted `working_dir`, fall back to the literal `"."` (`tools-mcp-local/src/tools/pwsh.rs:57`).
3. **Validate non-empty `working_dir` (only when explicitly provided)** — When the caller supplied `working_dir`, call `validation::validate_non_empty(working_dir, "working_dir", None)` (`tools-mcp-local/src/tools/pwsh.rs:58-62`). All-whitespace strings produce a tool-level error `"working_dir is required (non-empty string)"` (`tools-mcp-core/src/validation.rs:11-22`). The fallback `"."` (used when the caller omitted the field) bypasses this check.
4. **Resolve `working_dir` to a workspace-confined absolute path** — Call `path_policy::resolve_existing_directory(work_dir, "working_dir")` (`tools-mcp-local/src/tools/pwsh.rs:63-66`). This canonicalizes the server cwd, joins the input, canonicalizes the result, verifies it is inside the canonical workspace, and confirms it is an existing directory (`tools-mcp-local/src/path_policy.rs:47-63,183-225`). On failure, return `ToolCallOutcome::err(err.to_string())` with a message that ends in `"... resolves outside the server working directory <workspace>. Remediation: use a relative path under the server working directory, or an absolute path within that directory."`.
5. **Clamp `timeout_ms`** — Call `validation::clamp_timeout(req.timeout_ms, DEFAULT_PWSH_TIMEOUT_MS, 100, MAX_PWSH_TIMEOUT_MS)` (`tools-mcp-local/src/tools/pwsh.rs:67-72`). Default 60_000 ms; minimum 100 ms; maximum 300_000 ms (5 minutes). Callers passing `None` get the default; out-of-range values are clamped silently.
6. **Log intent** — Emit `info!("Pwsh tool: executing command in {}", work_dir.display())` (`tools-mcp-local/src/tools/pwsh.rs:74`). The command string is NOT logged at `info` level.
7. **Build the `pwsh` command** — Construct `Command::new(default_pwsh_exe())` with arguments `["-NoLogo", "-Command", <req.command>]`, set `current_dir(work_dir)`, and set both stdout and stderr to `Stdio::piped()` (`tools-mcp-local/src/tools/pwsh.rs:38-44`). The binary is `pwsh.exe` on `target_os = "windows"` and `pwsh` everywhere else (`tools-mcp-local/src/tools/pwsh.rs:30-36`). No environment-variable scrubbing is performed; the child inherits the server's environment.
8. **Spawn the child** — Call `cmd.spawn()` (`tools-mcp-local/src/tools/pwsh.rs:46-49,76`). On failure (typically `ENOENT` because `pwsh` is not on PATH), log `error!` and return `ToolCallOutcome::err(format!("failed to run pwsh: failed to spawn pwsh: {e}. Remediation: install PowerShell 7 (pwsh) and ensure it is on PATH."))` (`tools-mcp-local/src/tools/pwsh.rs:78-83`).
9. **Wait with bounded capture** — Hand the spawned `Child` to `wait_with_limits(child, timeout_ms, MAX_PWSH_STDOUT_BYTES, MAX_PWSH_STDERR_BYTES)` (`tools-mcp-local/src/tools/pwsh.rs:86-91`). This:
   - Takes the stdout and stderr pipes; if either is missing, kills the child within a 2 s grace period and returns an error (`tools-mcp-core/src/process.rs:100-113,148-151`).
   - Spawns one Tokio task per stream to drain into a `Vec<u8>` capped at the byte limit; the task continues reading past the cap (discarding overflow) so the child does not block on a full pipe (`tools-mcp-core/src/process.rs:49-76,115-118`).
   - Wraps `child.wait()` in `tokio::time::timeout(Duration::from_millis(timeout_ms), ...)` (`tools-mcp-core/src/process.rs:121-127`).
   - On timeout, calls `child.start_kill()` and waits up to `KILL_GRACE_MS = 2_000` ms; if the child does not exit, returns an error message describing the failed kill (`tools-mcp-core/src/process.rs:21,153-169`).
   - Joins both capture tasks and performs UTF-8 lossy conversion on the captured bytes (`tools-mcp-core/src/process.rs:129-133`).
   - Returns a `ProcessResult { exit_code, success, timed_out, stdout, stderr, truncated_stdout, truncated_stderr }` where `success` is `status.success() && !timed_out` (`tools-mcp-core/src/process.rs:135`).
10. **Translate wait/capture failures into tool errors** — If `wait_with_limits` returns `Err`, log `error!` and return `ToolCallOutcome::err(format!("failed to run pwsh: {e}"))` (`tools-mcp-local/src/tools/pwsh.rs:95-98`). This covers missing-pipe failures, wait-after-kill failures, and the kill-grace-exceeded path.
11. **Strip ANSI escapes** — Replace `result.stdout` and `result.stderr` with the output of `strip_ansi_codes(...)` (`tools-mcp-local/src/tools/pwsh.rs:101-102`). The stripper handles CSI sequences, OSC sequences (BEL or ESC\\-terminated), charset designation escapes, and single-character escapes (`tools-mcp-core/src/text.rs:21-96`).
12. **Log non-success outcomes** — If `result.success` is false, emit `error!("Pwsh tool: command failed (exit_code={:?}, timed_out={})", result.exit_code, result.timed_out)` (`tools-mcp-local/src/tools/pwsh.rs:104-109`).
13. **Build the JSON payload** — Construct `serde_json::json!({ "exit_code": ..., "success": ..., "timed_out": ..., "truncated_stdout": ..., "truncated_stderr": ..., "stdout": ..., "stderr": ... })` (`tools-mcp-local/src/tools/pwsh.rs:111-119`).
14. **Wrap as MCP content** — Return `ToolCallOutcome::ok_json_content(&payload, !result.success)` (`tools-mcp-local/src/tools/pwsh.rs:120`). The payload is serialized as compact JSON text content; `isError` is `true` when the command did not succeed (non-zero exit or timeout).

### 6.3 Response Schema

**Success-envelope shape (`isError` is `false` only when the command succeeded):**

```json
{
  "content": [
    {
      "type": "text",
      "text": "{\"exit_code\":0,\"success\":true,\"timed_out\":false,\"truncated_stdout\":false,\"truncated_stderr\":false,\"stdout\":\"hello\\n\",\"stderr\":\"\"}"
    }
  ],
  "isError": false
}
```

The handler always builds the same payload shape regardless of command success. `isError` mirrors the command's process-level result.

| Field (inside `content[0].text` JSON string) | Type | Always present | Description |
|---|---|---|---|
| `exit_code` | integer or `null` | Yes | The child's exit code; `null` when the process was killed by signal or timeout (`tools-mcp-core/src/process.rs:32,134`). |
| `success` | boolean | Yes | `true` iff `exit_code == 0` and no timeout occurred (`tools-mcp-core/src/process.rs:135`). |
| `timed_out` | boolean | Yes | `true` iff the wall-clock timeout fired and the child was killed (`tools-mcp-core/src/process.rs:124,140`). |
| `truncated_stdout` | boolean | Yes | `true` iff stdout exceeded `MAX_PWSH_STDOUT_BYTES = 1_000_000` (`tools-mcp-core/src/process.rs:67-71,143`). |
| `truncated_stderr` | boolean | Yes | `true` iff stderr exceeded `MAX_PWSH_STDERR_BYTES = 500_000` (`tools-mcp-core/src/process.rs:67-71,144`). |
| `stdout` | string | Yes | ANSI-stripped, UTF-8-lossy stdout (`tools-mcp-local/src/tools/pwsh.rs:101`). Empty string when the child wrote nothing. |
| `stderr` | string | Yes | ANSI-stripped, UTF-8-lossy stderr (`tools-mcp-local/src/tools/pwsh.rs:102`). Empty string when the child wrote nothing. |

| Envelope field | Type | Always present | Description |
|---|---|---|---|
| `content[0].type` | string | Yes | Always `"text"`. |
| `content[0].text` | string | Yes | A JSON-serialized string of the payload above. Callers MUST parse this string to recover structured fields. |
| `isError` | boolean | Yes | `false` when `success` is `true`; `true` when `success` is `false` (non-zero exit, timeout, or missing-pipe path). |

**Tool-level error envelope (`isError: true`) without a payload — used when the handler aborts before the child exits:**

```json
{
  "content": [{"type": "text", "text": "<message>"}],
  "isError": true
}
```

These error envelopes are produced via `ToolCallOutcome::err` (`tools-mcp-core/src/tool_outcome.rs:35-40`). The handler MUST NOT panic; all failure paths MUST return a `ToolCallOutcome`.

Note: When the command runs to completion but fails (non-zero exit or timeout), `isError` is `true` AND `content[0].text` still contains the full `{exit_code, success, timed_out, truncated_stdout, truncated_stderr, stdout, stderr}` JSON payload. Callers cannot distinguish a "handler-aborted" error envelope from a "command-failed" error envelope by `isError` alone; they MUST parse the text content and check whether it is valid JSON matching the payload schema.

### 6.5 Default flag set passed to `pwsh`

The command line constructed by `build_pwsh_command` is exactly (`tools-mcp-local/src/tools/pwsh.rs:38-44`):

```
<pwsh-binary> -NoLogo -Command <caller's command string>
```

Notes:

- The handler passes `-NoLogo` but does NOT pass `-NoProfile`, `-NonInteractive`, or `-ExecutionPolicy`. PowerShell profile scripts (`$PROFILE`) WILL run for the spawned process if they exist on the host. The justfile uses `-NoProfile` for its own scripts (`justfile:1,56`) but the MCP tool does not.
- The caller's command string is passed as a single argv element after `-Command`. PowerShell parses it as a single script block; multi-statement input is supported via `;` and newlines inside the string.
- The child inherits the parent process environment in full; there is no scrubbing of secrets, `PATH`, or other variables.

## 7. Security Considerations

This is the highest-impact tool in the registry. The threat model (`docs/tools-mcp-threat-model.md`) classifies `Pwsh` execution as a `critical` capability when its gate is bypassed.

- **Arbitrary host command execution.** Once registered, `Pwsh` will run any PowerShell expression the caller supplies. There is no command allowlist, no syntax validation, and no in-process sandbox. The only authorization gate is the startup-time `MCP_ENABLE_PWSH_TOOL=true` check (`tools-mcp-local/src/tools/mod.rs:30`). Operators MUST treat enabling the tool as equivalent to granting the calling client shell access to the host account that runs the server.
- **Disabled by default, enabled per-deployment.** The default registry build does NOT register `Pwsh`. The deployment is responsible for opting in. The threat model explicitly notes that this gate is "not enforced in this repository" beyond the env check (`docs/tools-mcp-threat-model.md`). Production deployments SHOULD treat enabling the tool as a separate change-control event.
- **Untrusted input MUST NOT be funneled into `command`.** Callers MUST NOT take a string from `WebFetch` output, file contents, or any other external source and pass it through to `Pwsh`. The tool has no defense against prompt-injection or string-template injection — see `docs/security.md` for the project's trust-boundary rules. The threat model documents the abuse path "prompt-injected `WebFetch` content driving a trusted agent into `Pwsh`" as a `high`-severity scenario.
- **Working directory is workspace-confined.** `path_policy::resolve_existing_directory` canonicalizes both the workspace and the candidate path and rejects any `working_dir` that resolves outside the server's cwd (`tools-mcp-local/src/path_policy.rs:47-63,303-322`). This includes `..` traversal and absolute paths pointing elsewhere. Tested by `pwsh_rejects_parent_traversal_working_dir_before_spawn` (`tools-mcp-local/src/tools/pwsh.rs:128-142`). Note that the *command body* is not confined — a script can `cd` elsewhere or operate on arbitrary absolute paths once it is running.
- **Environment is inherited verbatim.** The spawned child sees the full parent environment. If the server was started with secrets in its environment (API keys, tokens), commands running through `Pwsh` can read them. Operators SHOULD avoid co-locating secrets with the MCP server process when the gate is enabled.
- **PowerShell profile scripts will execute.** The tool passes `-NoLogo` but NOT `-NoProfile`. A profile file on the host (e.g., `Microsoft.PowerShell_profile.ps1`) WILL run before the caller's command. If the profile sets up aliases, functions, or environment changes, those affect every `Pwsh` invocation.
- **Bounded resource consumption.** The tool enforces a wall-clock timeout (default 60 s, max 300 s), bounded stdout (1 MiB), and bounded stderr (500 KiB) (`tools-mcp-core/src/config.rs:25-34`). These limits prevent a runaway command from monopolizing the server or filling the response with arbitrarily large output. The drain-after-cap behavior in `read_to_end_limited` (`tools-mcp-core/src/process.rs:49-76`) prevents the child from blocking on a full pipe, which would otherwise let a noisy child consume the timeout budget while producing no observable output.
- **No sandboxing.** The tool does not use job objects, namespaces, seccomp, or any other OS-level isolation. The child runs with the same user identity, filesystem visibility, and network access as the MCP server process.
- **ANSI stripping is presentation cleanup only, not a security boundary.** `strip_ansi_codes` runs after capture and improves output readability for downstream agents (`tools-mcp-local/src/tools/pwsh.rs:101-102`). It does not prevent any class of attack; callers MUST still treat captured output as untrusted external content.
- **Output redaction is the caller's responsibility.** stdout and stderr are returned verbatim (minus ANSI escapes) without any secret-pattern matching. If a command prints credentials, they will appear in the response.

| Variable | Default | Description |
|---|---|---|
| `MCP_ENABLE_PWSH_TOOL` | unset | When the literal string `"true"`, the tool is registered. Any other value (including unset) leaves the tool out of the registry and emits a `warn!` log line at server startup (`tools-mcp-local/src/tools/mod.rs:30-36`). Read exactly once at registration time. |

The handler itself does not read any other environment variables. The spawned child inherits the full parent environment.

## 10. Examples

### 10.1 Minimal request

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "mcp/tools/call",
  "params": {
    "name": "Pwsh",
    "arguments": {
      "command": "Write-Output hello"
    }
  }
}
```

### 10.2 Success response

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"exit_code\":0,\"success\":true,\"timed_out\":false,\"truncated_stdout\":false,\"truncated_stderr\":false,\"stdout\":\"hello\\n\",\"stderr\":\"\"}"
      }
    ],
    "isError": false
  }
}
```

### 10.3 Non-zero exit (command-level failure)

The handler returns `isError: true` with the full payload so the caller can inspect `exit_code`, `stdout`, and `stderr`:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "mcp/tools/call",
  "params": {
    "name": "Pwsh",
    "arguments": {
      "command": "exit 5"
    }
  }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"exit_code\":5,\"success\":false,\"timed_out\":false,\"truncated_stdout\":false,\"truncated_stderr\":false,\"stdout\":\"\",\"stderr\":\"\"}"
      }
    ],
    "isError": true
  }
}
```

### 10.4 Timeout

A command that exceeds `timeout_ms` is killed; the response carries `timed_out: true` and `exit_code: null`:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "mcp/tools/call",
  "params": {
    "name": "Pwsh",
    "arguments": {
      "command": "Start-Sleep -Seconds 30",
      "timeout_ms": 200
    }
  }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"exit_code\":null,\"success\":false,\"timed_out\":true,\"truncated_stdout\":false,\"truncated_stderr\":false,\"stdout\":\"\",\"stderr\":\"\"}"
      }
    ],
    "isError": true
  }
}
```

If the child refuses to exit within the 2 s kill grace, the handler instead returns the bare error envelope:

```json
{
  "result": {
    "content": [{"type": "text", "text": "failed to run pwsh: process timed out after 200 ms and did not terminate"}],
    "isError": true
  }
}
```

### 10.5 Working-dir traversal rejected before spawn

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "mcp/tools/call",
  "params": {
    "name": "Pwsh",
    "arguments": {
      "command": "Write-Output should-not-run",
      "working_dir": ".."
    }
  }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "content": [{"type": "text", "text": "path rejected for 'working_dir': .. resolves outside the server working directory <workspace>. The resolved path must stay inside the server working directory <workspace>. Remediation: use a relative path under the server working directory, or an absolute path within that directory."}],
    "isError": true
  }
}
```

Behavior verified by `pwsh_rejects_parent_traversal_working_dir_before_spawn` (`tools-mcp-local/src/tools/pwsh.rs:128-142`).

### 10.6 Tool absent when gate is unset

When `MCP_ENABLE_PWSH_TOOL` is unset (or has any value other than `"true"`), the tool is NOT in `mcp/tools/list`:

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "mcp/tools/list",
  "params": {}
}
```

The response's `result.tools[*].name` array will not include `"Pwsh"`. A subsequent `mcp/tools/call { name: "Pwsh" }` will not reach the handler in this SDD — it will be rejected by the central dispatcher (which is outside this tool's scope). The server logs `Pwsh tool is disabled by default; set MCP_ENABLE_PWSH_TOOL=true to enable host shell execution` at startup (`tools-mcp-local/src/tools/mod.rs:33-35`).

### 10.7 Missing `pwsh` binary

If `pwsh` is not installed (or not on PATH), the spawn step fails:

```json
{
  "result": {
    "content": [{"type": "text", "text": "failed to run pwsh: failed to spawn pwsh: No such file or directory (os error 2). Remediation: install PowerShell 7 (pwsh) and ensure it is on PATH."}],
    "isError": true
  }
}
```

**Coverage gaps:**

- No targeted unit test exercises the spawn-failure remediation message text (`"Remediation: install PowerShell 7 (pwsh) and ensure it is on PATH."`).
- No integration test calls `Pwsh` end-to-end through the MCP server with `MCP_ENABLE_PWSH_TOOL=true` set and a real `pwsh` available; the golden contract test only verifies the tool's presence in `tools/list`, not its execution.
- No test verifies that `working_dir: None` defaults to the literal `"."` rather than rejecting (the test suite happens to run from the server cwd so the default path resolves).
- No test confirms that the response payload's `isError` field is the inverse of `success` for the non-zero-exit case.
- No test asserts that PowerShell profile scripts are NOT suppressed (i.e., that `-NoProfile` is intentionally absent); this is a behavioral invariant that depends on host configuration to observe.

## 12. Open Questions

1. Should the tool pass `-NoProfile` and `-NonInteractive` to avoid running host profile scripts and to make the spawned process behave deterministically across hosts? The current behavior inherits whatever the user's profile sets up, which conflicts with the "uniform syntax across hosts" design goal in §5.
2. Should the `working_dir` check distinguish between the caller-provided `"."` case and the omitted case? Today, both paths reach `resolve_existing_directory(".")`, but only the explicit case is screened by `validate_non_empty`. This is consistent but possibly surprising.
3. Is it intentional that a non-zero exit code returns `isError: true` *and* the full JSON payload? Callers parsing only `isError` cannot distinguish a "handler aborted before running the command" envelope from a "command ran and failed" envelope without parsing the text content. Documenting this as the contract may be preferable to changing it, but the question is whether the dual signaling is by design.

## 13. Resolved Questions

| # | Question | Resolution |
|---|---|---|
| 1 | Does the tool have any aliases? | No. `McpTool::ALIASES` is not overridden, so the default `&[]` from `tools-mcp-core/src/tool_registry.rs:15` applies. Only the canonical name `"Pwsh"` resolves. |
| 2 | What happens to `mcp/tools/call { name: "Pwsh" }` when the gate is unset? | The tool is absent from the registry; the central dispatcher (`tools-mcp-core/src/tool_registry.rs:113-116`) finds no executor and returns `None`, which the server translates into a JSON-RPC tool-not-found response. The handler in this SDD is never invoked. |
| 3 | Is `MCP_ENABLE_PWSH_TOOL` re-read per call? | No. It is read once during `register_tools` at server startup (`tools-mcp-local/src/tools/mod.rs:30`). Changing the variable after startup has no effect. |
| 4 | Does the tool support `powershell.exe` (Windows PowerShell 5.1) as a fallback? | No. The selector only emits `pwsh.exe` or `pwsh` (`tools-mcp-local/src/tools/pwsh.rs:30-36`). A host without PowerShell 7+ produces a spawn-failure error. |
| 5 | Are stdout/stderr returned with ANSI escapes intact? | No. `strip_ansi_codes` runs unconditionally after capture (`tools-mcp-local/src/tools/pwsh.rs:101-102`). |
